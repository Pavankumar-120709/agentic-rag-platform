# Agentic RAG Engineering & System Design Interview Preparation

This document outlines key technical concepts, design trade-offs, and deep-dive answers for engineering interviews covering advanced RAG architectures.

---

## 1. Retrieval Architecture & Mathematics

### Q1: Why use Hybrid Retrieval instead of Dense Vector Retrieval alone?
**Answer:**
Dense embeddings excel at capturing semantic similarity and conceptual intent (e.g. mapping *"cardiac infarction"* to *"heart attack"*). However, dense models struggle with:
1. Exact match keywords, SKU numbers, product identifiers, and error codes (e.g., `ERR_CONN_REFUSED_404`, `RFC-7231`).
2. Rare domain acronyms and entity names that were infrequent in the pre-training corpus.
3. Out-of-vocabulary technical jargon.

Sparse BM25 provides exact token frequency and inverse document frequency matching. Combining dense and sparse models produces complementary recall that neither system can achieve independently.

### Q2: Why Reciprocal Rank Fusion (RRF) instead of linear score combination $(\alpha \cdot S_{\text{dense}} + (1-\alpha) \cdot S_{\text{sparse}})$?
**Answer:**
Raw scores from dense search and BM25 cannot be directly added because:
- Cosine similarity produces scores in $[-1, 1]$ or $[0, 1]$.
- BM25 produces unbounded scores in $[0, \infty)$ dependent on document length and corpus size.
- Score calibration (such as min-max scaling or z-score normalization) is sensitive to outliers and distribution shifts.

**Reciprocal Rank Fusion (RRF)**:
$$RRF(d) = \sum_{m \in M} \frac{1}{k + \text{rank}_m(d)}$$
Where $k$ is a smoothing constant (standard: 60).
- RRF is strictly rank-based and scale-invariant.
- It prevents a high BM25 outlier score from dominating dense semantic matches.
- Documents that appear consistently in the top 20 of both systems receive an amplified boost over documents appearing in only one.

### Q3: How does a Cross-Encoder Reranker differ from Bi-Encoder Vector Search?
**Answer:**
- **Bi-Encoder (Dense Search)**: Encodes query $q$ and document $d$ into vectors $E(q)$ and $E(d)$ independently. Candidate retrieval is fast ($O(\log N)$ with HNSW indexing) because dot product / cosine similarity is computed across pre-indexed vectors. However, there is zero cross-attention between query tokens and document tokens.
- **Cross-Encoder**: Passes $(q, d)$ concatenated together through full transformer self-attention layers: $\text{CrossAttention}(q, d)$. Every query token attends directly to every document token, capturing fine-grained relationships, negation, and word order. Because cross-encoders are computationally expensive ($O(N)$ transformer forward passes), they are used as a 2nd-stage reranker over the top $K$ fused candidates (e.g., $K=20 \to 5$).

## 2. Agentic Orchestration & LangGraph

### Q4: Why use a Bounded Graph (LangGraph) instead of an open-ended Autonomous Agent?
**Answer:**
Open-ended autonomous loops (e.g. ReAct loops without termination bounds) suffer from:
1. Infinite loops when queries are out-of-domain.
2. Latency non-determinism (unpredictable token usage and response times).
3. Cost compounding.

This architecture enforces **bounded state graphs**:
- Max query rewrites: 2.
- Max regeneration attempts: 1.
- Deterministic conditionals: if evidence quality remains below threshold after 2 rewrites, the agent transitions deterministically to `fallback_answer` (abstention) rather than continuing to speculate.

### Q5: How do you validate citations deterministically without trusting LLM self-evaluation?
**Answer:**
LLMs frequently hallucinate citations by referencing real authors or guessing chunk IDs.
Our pipeline enforces **deterministic two-stage verification**:
1. **ID Validation**: Every `chunk_id` in the output citation list must exist in the `selected_context` array passed to the LLM. Unknown chunk IDs are rejected immediately.
2. **Quotation Verification**: The `quoted_text` must exist as a verbatim substring (or normalized sequence match $>85\%$) in the body of that referenced chunk.
3. If quotes or chunk IDs fail validation, the answer is flagged as ungrounded and routed to bounded regeneration.

## 3. Evaluation & Production Engineering

### Q6: What are the fundamental limitations of RAGAS and LLM-as-a-Judge metrics?
**Answer:**
1. **Self-Consistency Bias**: Models tend to score outputs generated by their own model family higher.
2. **Position Bias & Verbosity Bias**: Longer, more verbose answers often receive higher relevancy scores even if they introduce irrelevant details.
3. **Imperfect Ground Truth**: Benchmark test sets can become stale as documentation changes.
4. **Latency & Cost**: Running LLM-as-a-Judge evaluations on live production traffic introduces significant latency and cost; therefore, evaluation should be performed on offline benchmark runs and sampled shadow traffic.

### Q7: How does this system defend against Prompt Injection in retrieved documents?
**Answer:**
Documents are treated as untrusted data inputs.
1. Regular expressions scan for injection triggers (`ignore previous instructions`, `disregard system prompt`, `system: you are now`).
2. Structured generation prompts clearly delineate context chunks using demarcated boundaries:
   `--- [CHUNK ID: ...] ---\n<untrusted content>`
3. System instructions explicitly dictate that text inside context chunks must only be used as evidence and never executed as procedural commands.
